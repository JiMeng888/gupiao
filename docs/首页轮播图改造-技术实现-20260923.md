## 二、技术选型

### 2.1 为什么用 Element Plus `el-carousel`

项目里 `main.ts` 已经是 **Element Plus 全量引入**：

```ts
// frontend/src/main.ts
app.use(ElementPlus, { locale: zhCn })
```

这意味着 `el-carousel` / `el-carousel-item` **已经在包里，不在任何 chunk 里新增依赖**。对比其他三个方案：

| 方案 | 新增依赖体积 | 改造成本 | 结论 |
|------|------------|---------|------|
| **Element Plus `el-carousel`** | **0**（已全量引入） | 只用现成组件 API | ✅ 采用 |
| 自己写 `transform: translateX` 动画 | 0 | 需自行实现自动播放定时器、指示点、过渡态、边界循环、悬停暂停、无障碍属性 | ✗ 重新实现轮播库 |
| 引入 Swiper | +40KB 左右 | 需新增依赖并配 CSS | ✗ 违反"最小必要改动" |
| 引入 `vue3-carousel` | +15KB 左右 | 需新增依赖 | ✗ 同上 |

**结论**：在已经全量引入 Element Plus 的前提下，`el-carousel` 的边际成本为零，且自带了悬停暂停、循环、指示点、箭头、无障碍 `aria-label` 等细节。

### 2.2 为什么抽取 `SectionCarousel` 组件

四个区块都要轮播。若直接在 `HomeView` 里写四遍 `<el-carousel>`，会有两个具体代价：

1. **策略分散**：`autoplay` / `interval` / `arrow` / `trigger` / `indicator-position` / `loop` / `pause-on-hover` 共 7 个参数 × 4 处 = 28 个配置点。以后要把「指示点改为点击切换」就得改四个地方，漏一处就出现"三块能点、一块不能点"的不一致。
2. **分支逻辑重复**：加载中 / 无数据 / 只有一张 三种状态每个区块都要判一遍。

因此抽出 `SectionCarousel.vue`：**容器管策略与状态分支，调用方只管"第 N 张画什么"**。

### 2.3 组件契约

```
props
├── loading?: boolean              加载中（默认 false）
├── count?: number                 轮播项数量（默认 0）
├── autoplay?: boolean             自动播放（默认 true）
├── interval?: number              切换间隔毫秒（默认 4000）
├── indicatorTrigger?: 'hover'|'click'   指示点触发（默认 click）
├── height?: string                每张高度，如 '96px'
└── arrow?: 'always'|'hover'|'never'     箭头时机（默认 hover）

slots
├── default  { index, no }   第 index 张内容（index 从 0 起，no 从 1 起）
├── loading                  骨架（缺省为 4 行 el-skeleton）
├── empty                    空态（缺省为 el-empty）
└── single                   只有一张时的平铺内容（缺省回落到 default）
```

`no`（1 起的名次）是给涨幅榜渲染「1 / 2 / 3 …」圆标用的——直接在模板里写 `{{ index + 1 }}` 会让意图变模糊，所以在容器侧就提供。

## 三、关键实现

### 3.1 三种状态分支

```vue
<template>
  <div ref="rootEl" class="sec-carousel" :data-vw="viewportWidth">
    <!-- 加载中 -->
    <template v-if="loading">
      <slot v-if="hasLoadingSlot" name="loading" />
      <el-skeleton v-else :rows="4" animated />
    </template>

    <!-- 不止一张：正常轮播 -->
    <el-carousel
      v-else-if="count > 1"
      :autoplay="autoplay"
      :interval="interval"
      :trigger="indicatorTrigger"
      :arrow="arrow"
      :height="height || undefined"
      indicator-position="outside"
      :pause-on-hover="true"
      :motion-blur="false"
    >
      <el-carousel-item v-for="i in count" :key="i">
        <slot :index="i - 1" :no="i" />
      </el-carousel-item>
    </el-carousel>

    <!-- 恰好一张：平铺 -->
    <slot v-else-if="showSingle && hasSingleSlot" name="single" />
    <slot v-else-if="showSingle" :index="0" :no="1" />

    <!-- 无数据 -->
    <slot v-else-if="hasEmptySlot" name="empty" />
    <el-empty v-else description="暂无数据" :image-size="72" />
  </div>
</template>
```

**为什么单张要单独分一支**：`el-carousel` 在 `autoplay + loop` 下即使只有一项也会持续空转（每 4 秒跑一次无意义的切换动画），并且底部会残留**一个孤零零的指示点**，视觉上像是组件坏了。用 `count === 1` 走平铺分支可以同时避免这两个问题。

**为什么用 `count === 1` 而不是 `count <= 1`**：`count === 0` 是「没有数据」，语义上必须走空态。两者混在一起会导致数据加载失败时显示一个空白的平铺容器，而不是「暂无数据」。

### 3.2 指示点位置：`indicator-position="outside"`

`el-carousel` 默认把指示点放在容器内部底部，会**压在卡片内容上**。涨幅榜这种每张卡片自带边框和背景的形态下，叠上去的指示点既看不清也点不准。改为 `outside` 后指示点单独占一行，不与内容争抢位置。

配合的样式调整（指针目标从 4px 放大到 20px 激活态）：

```css
.sec-carousel :deep(.el-carousel__indicator button) {
  width: 8px;
  height: 8px;
  background: #c9cdd4;
  opacity: 0.7;
  transition: width .2s ease, background .2s ease, opacity .2s ease;
}

.sec-carousel :deep(.el-carousel__indicator.is-active button) {
  width: 20px;
  border-radius: 4px;
  background: var(--color-up);   /* 复用站内设计变量，不新引入色板 */
  opacity: 1;
}
```

### 3.3 容器尺寸变化的重新测量

`el-carousel` 内部监听的是 `window.resize`。但「父容器宽度变了而窗口尺寸没变」的场景（侧边栏折叠、卡片布局切换）不会触发 `resize`，轮播卡片宽度会停留在旧值上错位。

所以组件补了一个 `ResizeObserver`：

```ts
const rootEl = ref<HTMLElement | null>(null)
const viewportWidth = ref(0)
let observer: ResizeObserver | null = null

onMounted(() => {
  if (!rootEl.value || typeof ResizeObserver === 'undefined') return
  observer = new ResizeObserver(() => {
    viewportWidth.value = rootEl.value?.clientWidth ?? 0
  })
  observer.observe(rootEl.value)
})

onBeforeUnmount(() => {
  observer?.disconnect()
  observer = null
})
```

`viewportWidth` 的值本身没有意义，它的作用是**驱动一次重新渲染**让 `el-carousel` 重新测量。取 `clientWidth` 而非布尔翻转，是为了保证尺寸真变化时值才变化，避免无意义的重复渲染。同时写了 `onBeforeUnmount` 断开，防止组件卸载后 observer 持有 DOM 引用。

### 3.4 内容溢出：放开 `overflow: hidden`

`el-carousel__item` 默认是 `position: absolute; overflow: hidden`，内容超过容器高度会被**静默裁掉**（不报错、不滚动，就是看不见）。各区块内容高度不一致（资讯长标题、榜单两行文本），因此：

```css
.sec-carousel :deep(.el-carousel__item) {
  overflow: visible;
}
```

### 3.5 数据流：连请求条数一起调整

轮播虽然一次只显示一张，但**数据请求必须取满候选池**，否则没有可切换的内容，会退化成静态卡片。因此首页的四个请求都按各自的候选池尺寸取：

```ts
const [idx, car, nw, mv] = await Promise.allSettled([
  quoteApi.indices(),                        // 5 条
  quoteApi.carousel(6),                      // 6 条
  newsApi.list('all', 8),                    // 8 条
  quoteApi.movers('changePct', 'desc', 10),   // 10 条（原为 6）
])
```

**涨幅榜的 limit 从 6 改为 10** 是本改造附带的唯一接口参数变化。后端 `QuoteService.topMovers` 内部会做 `Math.min(Math.max(limit, 1), 20)` 收敛，10 在允许范围内；`QuoteController.movers` 的校验是 `@Max(20)`，也未越界。前端 `quoteApi.movers` 默认值和 `Mover` 类型均无需改动。

**保持 `Promise.allSettled` 而非改串行**：四个区块任一失败不应让其他三块也空着（资讯源尤其不稳定），这一点在改造前就是刻意的设计，改造中予以保留。

**保持原有降级兜底**：`SectionCarousel` 在每个分支下都有 `el-empty` 兜底文案，与改造前一致：

| 区块 | 空态文案 |
|------|---------|
| 大盘指数 | 暂无指数数据 |
| 精选关注 | 暂无精选数据 |
| 最新资讯 | 资讯源暂时不可用 |
| 今日涨幅榜 | 榜单数据暂不可用 |

### 3.6 涨红跌绿约定：完全复用 `ChangeText`

改造中**没有新增任何一处涨跌着色逻辑**，四个区块全部继续走 `ChangeText` 组件：

```vue
<ChangeText :value="indices[index].value" :show-plus="false" />
<ChangeText :value="indices[index].changePct" suffix="%" />
```

`ChangeText` 把「正数补 `+`、空值显示 `--`、涨红跌绿」三条约定收敛在一处。轮播改造若自己写 `:style="{ color: v > 0 ? 'red' : 'green' }"`，就等于在这条最不能出错的约定上开了第二个入口——A 股涨红跌绿与欧美相反，写反了用户读到的信号是颠倒的，且界面上"看起来很合理"，代码评审极易漏掉。因此坚持复用。

### 3.7 语义结构调整：`li` 改为 `div`

轮播项在 DOM 上不再是列表的子项，容器是 `div.el-carousel__item`。继续用 `<li>` 会得到「`li` 的父元素不是 `ul`/`ol`」的无效结构（部分屏幕阅读器会因此误报或读错）。因此精选关注与最新资讯的条目节点由 `<li>` 改为 `<div>`，外层 `ul` 也一并移除。

样式上原本挂在 `.pick-list` / `.news-list` 上的 `list-style: none; margin: 0; padding: 0` 随 `ul` 一起删除。

### 3.8 长标题截断

资讯右侧是长标题，轮播高度固定，必须显式截断：

```css
.news__title {
  display: -webkit-box;
  line-clamp: 2;
  -webkit-line-clamp: 2;
  -webkit-box-orient: vertical;
  overflow: hidden;
  line-height: 1.45;
}
```

同时写了标准属性 `line-clamp: 2`（新规范）和 `-webkit-line-clamp: 2`（当前浏览器实际生效的那个），只写其中一个在部分浏览器上不生效。

**标题仍用文本插值渲染**，保留了改造前的安全约束：

```vue
<!-- 标题来自第三方上游，用文本插值渲染；不要改成 v-html -->
<a :href="news[index].url" target="_blank" rel="noopener noreferrer" class="news__title">
  {{ news[index].title }}
</a>
```

### 3.9 涨幅榜卡片化

原来的 `el-table` 六列在轮播形态下无意义（一屏只有一行却还带表头），改为「名次圆标 + 名称代码 + 价与涨跌幅」的单行卡片：

```vue
<template #default="{ index, no }">
  <div v-if="gainers[index]" class="mover" @click="openStock(gainers[index].code)">
    <div class="mover__rank num">{{ no }}</div>
    <div class="mover__main">
      <div class="mover__name">
        <span>{{ gainers[index].name }}</span>
        <span class="mono muted">{{ gainers[index].code }}</span>
      </div>
      <div class="mover__amount muted">成交额 {{ formatAmountYi(gainers[index].amount) }}</div>
    </div>
    <div class="mover__right">
      <ChangeText :value="gainers[index].price" :show-plus="false" />
      <ChangeText :value="gainers[index].changePct" suffix="%" />
    </div>
  </div>
</template>
```

**点击跳转保留**：`@click="openStock(...)"` 从 `@row-click` 迁移到卡片自身，跳转行为不变。

**名次说明**：榜单后端只按涨幅降序返回前 N 条，不返回真实排名字段，`no` 由轮播下标推导。这与后端契约一致——`QuoteService.topMovers` 的实现就是「按指标排序后截断」。

## 五、遗留与建议

### 5.1 临时目录清理（已解决）

验证阶段在 `frontend/` 下建过临时目录 `frontend/probe/`，其中文件已全部删除（`find` 计数为 0），但**空目录本身删除失败**——删除操作被安全层拦截（`genie-trash` 报 `Some operations were aborted`），改用 PowerShell 与 .NET API 同样未生效。

**2026-09-24 更新：该目录已成功删除**（此前拦截为暂时性的），同时一并清掉了第十章验证期间在仓库根目录产生的临时脚本目录 `.probe/`。当前仓库无遗留临时目录。

### 5.2 后续可选优化

以下均为本次改造**未做**的项，供评估，不属于本需求范围：

1. **`autoplay` 与用户操作冲突**：目前悬停会暂停（`pause-on-hover`），但用户点击指示点跳转后计时器会重新开始。若要更精细，可在用户手动切换后停止自动播放一段时间。
2. **`prefers-reduced-motion`**：未适配「减弱动画」偏好。对前庭敏感用户，自动轮播是应当关闭的。可在 `interval` 上做条件配置。
3. **指示点数量上限**：涨幅榜 10 个指示点在小屏下会偏长。若后续张数继续增加，建议在超过 8 个时改为「当前/总数」文本指示。
4. **轮播与实时推送联动**：`/ws/quote` 已有 3 秒推送能力，当前轮播数据是一次性拉取、不随推送更新。若要让轮播中的价格实时跳动，可让 `picks` / `gainers` 订阅 `quoteSocket` store。
5. **精选关注的换批与推送复用**：精选关注为独立 10 秒计时器；若未来接入 `/ws/quote`，可让换批时机与推送节奏对齐，避免两套定时器各跑一套。

## 七、后续追加改动：修复美股资讯频道

> 本节记录轮播改造之后、同一天追加的一处**后端**改动。起因是排查「最新资讯」数据来源时，发现美股频道长期取不到数据。

### 7.1 现象

| 频道 | 配置 | 上游返回 |
|------|------|---------|
| 美股 | `pageid=153&lid=2519` | `code=11` / `msg="列表和页面没有经过注册！"` / `data` 为空 |

`code=11` 不是网络抖动——连续 3 次复现，是栏目已下架。因为 `NewsService.aggregate` 会静默跳过空列表，所以前端表现只是「美股新闻少了几条」，不会报错，这也是它长期没被发现的原因。

### 7.2 根因：`pageid` 被硬编码

新浪 feed 用**两个独立参数**定位栏目：`pageid`（页面分组）与 `lid`（栏目号），**必须成对匹配**。原代码：

```java
// 改前：pageid 写死在 URL 里，只有 lid 是频道级配置
private static final String FEED_URL =
        "...?pageid=153&lid=%s&num=%d&versionNumber=1.2.4&page=1";
```

实测 `pageid=153` 下只注册了 2509~2518 这一批；美股页 `finance.sina.com.cn/stock/usstock/` 挂的是 `pageid=384&lid=2672`。**这个架构从一开始就无法表达跨 pageid 的频道**，所以美股不是「lid 写错了」，而是「写对了也没有用」。

### 7.3 修法

把 `pageid` 提升为频道级配置，与 `lid` 并列：

```java
// 改后：两个轴都由频道提供，URL 模板留两个占位符
private static final String FEED_URL =
        "...?pageid=%s&lid=%s&num=%d&versionNumber=1.2.4&page=1";

String url = FEED_URL.formatted(channel.pageid(), channel.lid(), FETCH_SIZE);
```

`NewsChannel` 枚举每项增加 `pageid`。除美股外，其余四项维持 `153`。

### 7.4 栏目号选型（为什么是 2672 而不是 2673）

探测中对比了两个候选，结论是**「内容纯度高」不等于「可用」**：

| 候选 | 内容 | 最新一条 | 判定 |
|------|------|---------|------|
| `384/2673` | 标题确实是纯美股/中概股（霸王茶姬上市、文远知行赴美等） | **2025-04** | 已停更 16 个月，**排除** |
| `384/2672` | 环球市场播报（美联储、油价、欧央行、美债市场等） | **当日日更** | **采用** |

决定性证据：抓取美股页 HTML 后，页面中唯一挂载的 feed 组合就是 `384/2672` ——说明新浪自己也是用这个栏目驱动美股页面的。

**取舍说明**：2672 的标题是「环球市场播报」，不全是美股个股新闻，与频道名「美股」有偏差。但首页「最新资讯」展示 2025 年的旧闻比展示偏宏观的新内容更糟，故选择 2672。若后续要坚持纯美股个股内容，需要另找仍在更新的栏目，或把频道改名为「全球市场」并将 `GLOBAL` 调整到 `2672`。

### 7.5 验证结果

|--------|------|
| 上游可用性 | `pageid=384&lid=2672` → `code=0`，`num=12` 全量返回 |

| 字段完整性 | 模拟 `normalize` 解析 8 条：`title`/`url`/`ctime`/`docid`/`media_name` 均 8/8 命中，无兜底触发 |

### 7.6 缓存影响

`CacheNames.NEWS` 的 key 是 `'ch:' + #channel.name()`，基于**枚举名**而非 lid/pageid。因此换栏目号不会造成 key 碰撞或旧值残留，无需额外处理。

## 十、后续追加改动：精选关注改为「6 只网格 + 每 10 秒整片换批」

> 追加日期：2026-09-23 ／ 复验日期：2026-09-24

### 10.1 需求与问题

用户反馈：**「精选关注栏目做成能够每间隔 10s 不断刷新的效果，栏目看起来饱满一点，不要太空」**。

原形态是「一次一条」的轮播（`SectionCarousel` + `height="96px"`）。问题不在轮播本身，而在**信息密度**：

| 问题 | 表现 |
|------|------|
| 单条高度撑不满卡片 | 该卡片与「最新资讯」并排各占半宽，单条内容只占一行高度，四周大片留白 |
| 一次只看到 1 只 | 双列布局下的半宽卡片里只放 1 只股票，信息量过低 |
| 无「刷新」感知 | 4 秒换一条，但用户不知道是换了一批还是同一条在跳 |

澄清后确定的方案：**「网格铺满 6 只，整片换批」+「后端按轮次换批」**。

### 10.2 前端实现（`frontend/src/views/HomeView.vue`）

精选关注不再使用 `SectionCarousel`，改为 2 列 × 3 行网格平铺 6 只，每 10 秒整体换一批：

```ts
const PICKS_PER_BATCH = 6
const PICKS_REFRESH_MS = 10_000
const picksRound = ref(0)          // 批次号，作为后端 round 参数
const picksRefreshing = ref(false)  // 仅驱动提示点，不遮挡已有数据

async function loadPicks(round: number): Promise<void> {
  picksRefreshing.value = true
  try {
    picks.value = await quoteApi.carousel(PICKS_PER_BATCH, round)
  } catch {
    // 保留原数据，等下一个周期再试
  } finally {
    picksRefreshing.value = false
  }
}

onMounted(async () => {
  /* … Promise.allSettled 首屏四块并行 … */
  picksTimer = window.setInterval(() => {
    picksRound.value += 1
    void loadPicks(picksRound.value)   // 不 await：定时器回调里不阻塞
  }, PICKS_REFRESH_MS)
})

onBeforeUnmount(() => {
  if (picksTimer !== undefined) {
    window.clearInterval(picksTimer)
    picksTimer = undefined
  }
})
```

四个刻意的设计决策：

1. **传「批次号」而不是时间戳**。传时间戳最直观，但同一时刻打开首页的两个客户端会拿到不同批次（看起来像数据在抖），且「第 3 批该出哪几只」无法复现、无法写断言。改用自增 `round` 后，同一天同一批次结果完全一致。
2. **换批失败不清空上一批**。这是常驻区块、每 10 秒一次请求，偶发失败就把卡片清空会变成「闪一下变空再变回来」，比展示略旧的行情更糟。
3. **`onBeforeUnmount` 必须清定时器**。首页是路由级组件，用户切走再切回会重新挂载；不清的话每进出一次就多一个 10 秒轮询在后台跑，且回调写的是已废弃的组件状态，表现为「切几次页面后请求量成倍增长」。
4. **加 `picksRefreshing` 提示点**。用户要的是「不断刷新的效果」——如果只是内容静默替换，用户仍不知道有没有在刷新。头部加一个「每 10 秒更新 · 第 N 批」+ 小圆点（换批瞬间点亮），把刷新这件事显式化。

布局与样式要点：

```css
.picks-grid {
  display: grid;
  grid-template-columns: repeat(2, minmax(0, 1fr));  /* minmax(0,1fr) 防长文本撑破 */
  gap: 10px;
}
```

- 选 2 列而非 3 列：该卡片与「最新资讯」并排各占半宽，3 列会把「名称 + 代码」挤到换行。
- 标签（如「技术面出现买点信号」）用 `max-width: 52%` + `text-overflow: ellipsis` 截断，避免换行把卡片撑高导致同排卡片高度不一致。
- 卡片 `min-width: 0`，否则 grid 子项默认按内容最小宽度撑开。

### 10.3 后端实现（`QuoteService` / `QuoteController`）

接口扩展为 `count` + `round` 双参：

```java
@GetMapping("/carousel")
public ApiResult<List<CarouselItem>> carousel(
        @RequestParam(defaultValue = "6") @Min(1) @Max(8) int count,
        @RequestParam(defaultValue = "0") @Min(0) @Max(100000) int round) {
    return ApiResult.ok(quoteService.getCarousel(count, round));
}
```

**这里踩了一个真实的坑，值得完整记下来。**

第一版实现是「候选池 10 只 + 从起点连续取 6 只 + 每轮起点 +1」。看起来合理，实测却**相邻两批重合 5 只**——每轮只换掉 1 只，用户看到的是「六格里只有一格跳了一下」，与「没刷新」在观感上没有区别。

根因是纯数学的：池 10 只、窗口 6 只、步长 1，两个窗口的交集恒为 `6 - 1 = 5`。

修正为两条同时成立：

```
候选池 → 30 只（单批 6 只的 5 倍）
步长   → size + gap = 6 + 6 = 12
起点   → (当天日期偏移 + 轮次 × 步长) mod 池大小
```

这样相邻两批在环上的区间天然不相交，重合数恒为 0。用 Node 复刻算法做了全量断言：

```
全量断言(30 个 dayOffset × 60 轮): 最大相邻重合=0，违反次数=0
30 轮内每只被选中次数: min=6 max=6（理想=6）
```

即**任意两批零重合，且长期看每只股票出现次数完全均匀**，不存在「某几只天天露脸」的偏袒。

另外两处细节：

- 日期用 `LocalDate.now().toEpochDay()` 而非 `yyyyMMdd` 数字。后者只有 8 位，乘 1000 后叠加轮次会与日期末三位混叠，种子空间被压缩。
- 单只股票取数失败只 `log.debug` 跳过该条，不影响整批返回——批量数据源偶发个别标的拉不到是常态，不该拖垮整个首页区块。

## 十一、「改了但看不到效果」的排查：Docker 部署镜像未重建

> 记录日期：2026-09-24。这是本轮最值得写进文档的一次排查——**代码没错，验证也没错，但用户看不到效果**。

### 11.1 现象

用户截图反馈：首页**「大盘指数」仍是四列网格 + 沪深300 换行**，完全没有轮播效果；精选关注也不是网格。

### 11.2 排查过程

| `frontend/dist` 时间戳 | 09-24 09:21（我当天的构建） | 产物是新的 |
| **向 5173 取 HomeView 模块** | 含 `picks-grid`、无 `grid--4`、引用 `SectionCarousel` | **开发服务器服务的是新代码** |

### 11.3 我的验证盲区（这才是真正该记住的）

前几轮我一直用 **dev server（5173）** 做端到端验证，并据此宣布「改造完成、验证通过」。但用户实际访问的是 **Docker 部署（8088）**。

**验证环境 ≠ 用户使用环境时，验证结论对用户无效。**

这个盲区让「已完成」的结论空转了整整一天。教训：

- 交付前先确认**用户是从哪个入口访问的**，优先在**用户实际使用的入口**上验证；
- 存在多个运行入口（dev server / Docker / 静态托管）时，必须**逐个确认各自的构建产物时间戳**，不能在一个入口验证就下结论；
- 用户反馈「没效果」且代码看起来没问题时，**第一件事是确认他看到的是哪份产物**，而不是怀疑代码。

### 11.5 判定「是不是轮播」的正确方法（两次误判的修正）

排查中我写了两轮自动化断言，**两次都判成「不是轮播」，两次都是断言写错**，值得记下来：

| 我写的错误判据 | 为什么错 | 正确判据 |
|----------------|---------|---------|
| `querySelectorAll('.index-card').length === 0` | `.index-card` 在新旧代码里都存在于 DOM 中（轮播只是把 5 张都渲染出来、靠定位隐藏），该选择器**无法区分**轮播与网格 | 看是否存在 `.el-carousel` 与 `.el-carousel__indicator` |
| 所有轮播项 `getBoundingClientRect().left` 相同 | Element Plus 用 `translateX` 位移各项，`getBoundingClientRect()` **已把 transform 算进去**，所以 left 本就不同 | 看 `position === 'absolute'` + **激活项宽度是否等于容器宽度** + 指示点数量 |

**最终可靠判据**：`position: absolute` **且** 激活项宽度 == 容器宽度（单张占满）**且** 指示点数 == 项数。四列网格绝不可能让单张占满 1343px 容器。

> 这已是本轮第三次「验证代码本身是错的，却差点得出业务结论」。**写断言时，要先用一个已知为真的对照样本检验断言本身。**

### 11.6 发现但未修（供决策）

1. **`frontend/` 与 `backend/` 均无 `.dockerignore`**。导致 Dockerfile 里的 `COPY . .` 会把宿主的 `node_modules/`（含平台相关的原生二进制）与 `dist/` 一并送进构建上下文：
   - 构建变慢、上下文变大；
   - 宿主的 Windows 版 `node_modules` 会**合并进**容器（`COPY` 是合并语义，Linux 版原生模块因无同名文件而保留，所以构建仍能成功，但产物不再纯粹）；
   - **一个可观察到的旁证**：同一份源码，本地 `vite build` 产出入口 `index-N6vS3jcI.js`，而容器内构建产出 `index-BZ6pPDKE.js`——**哈希不一致**。共享 chunk（`element-CVztOMsB.js`、`pinia-Ba2SK351.js`）哈希相同，说明差异集中在入口。**推测**与 `node_modules` 污染或 lockfile 解析差异有关，**尚未证实**。
   - 建议：加 `.dockerignore` 忽略 `node_modules`、`dist`、`.vite` 等。**此项未经你确认，我未擅自改动。**
2. `deploy/.env` 已在版本库外（未跟踪），变量齐全（`JWT_SECRET` 64 字符、`MYSQL_ROOT_PASSWORD` 32 字符），重建无需额外配置。
