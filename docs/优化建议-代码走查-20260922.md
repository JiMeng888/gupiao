## 二、P0：建议尽快修

### 1. 前端 20 秒超时 < 后端大模型 45 秒超时

**现象**：三个环节的超时预算互相不匹配，而**最短的那个在客户端**。

| 环节 | 配置 | 位置 |
|---|---|---|
| 浏览器 axios | **20 000 ms** | `frontend/src/api/http.ts:90` |
| Nginx 反代 | 120 s（注释里明确说是为 AI 链路留的） | `frontend/nginx.conf:67-68` |
| 后端大模型 | **45 s** | `application.yml:86` `app.llm.timeout: 45s` |

`analysisApi.regenerate` → `api.post` → 用的是 axios 实例的**全局 20s**，没有任何覆盖：

```ts
// frontend/src/api/http.ts
const http = axios.create({ baseURL: '/api/v1', timeout: 20_000 })

// frontend/src/api/endpoints.ts —— 无 timeout 覆盖
regenerate: (code: string) => api.post<AnalysisReport>(`/analysis/${encodeURIComponent(code)}`),
```

**为什么是必然失败而不是偶发**：配了 `LLM_API_KEY` 后，`AnalysisService#fromLlm` 会在请求线程上
同步等待大模型，而 DeepSeek / 千问 这类服务生成长文本（`max-tokens: 1500`）普遍需要
20~40 秒。**45 秒是"上限"而不是"预期值"**，所以 20s 的客户端超时会被稳定击穿。

**后果**：用户在「重新生成」按钮上等到 20 秒看到「无法连接服务器」，
而后端其实还在跑，几十秒后把报告写进了 `ai_reports`。用户再点一次 → 又一次超时。
只有手动刷新页面走 GET 才会拿到那份早已生成好的报告。**用户看到的现象是"AI 分析坏了"**。

**修复建议**（任一即可，推荐前两条一起做）：

```ts
// 方案 A：给 AI 相关请求单独放宽（最小改动）
post: <T>(url: string, data?: unknown, timeout?: number) =>
  request<T>({ method: 'POST', url, data, timeout })

// endpoints.ts
regenerate: (code: string) =>
  api.post<AnalysisReport>(`/analysis/${encodeURIComponent(code)}`, undefined, 60_000)

// 方案 B：全局提到 60s，并给行情类请求单独收紧到 10s
```

> 顺带确认过：`analysisApi.get`（GET）在**没有存档时会触发生成**，
> 所以 GET 也需要同样的超时放宽——不能只改 POST。

### 2. AI 报告存档没有时效，"降级报告"会被永久复用

`AiReportMapper.selectLatestByCode` 没有任何时间条件：

```java
@Select("SELECT * FROM ai_reports WHERE code = #{code} ORDER BY created_at DESC LIMIT 1")
AiReport selectLatestByCode(@Param("code") String code);
```

而 `AnalysisService.analyze` 的 GET 路径是「有存档就直接返回，不重新生成」。

**两个后果**：

1. **规则化降级报告会被永久固化**。没有配 `LLM_API_KEY` 时，`ruleBased()` 生成的报告
   也会走 `archive()` 落库。之后即使配好了 Key，`GET /analysis/{code}` 仍然返回那份
   `model=rule-based` 的旧报告，必须用户手动点「重新生成」才会换成大模型结果。
   对"上了 Key 但结果还是规则化"的排查者来说，这是个很难定位的坑。

2. **报告里的价格是死的，但措辞是"最新"**。报告正文由 `ruleThesis()` 拼出来：

   ```
   「贵州茅台（600519）最新价 1685.00，当日 +1.23%」
   ```

   这句话会被原样存进 `report_json`。三天后再 GET，页面仍然显示「最新价 1685.00」——
   而它既不是最新价，报告本身也没有任何"数据已过期"的标注。

**修复建议**：

- 在 `selectLatestByCode` 加时效窗口（建议做成配置，例如 `app.analysis.archive-max-age: 6h`）：

  ```sql
  SELECT * FROM ai_reports
  WHERE code = #{code} AND created_at >= #{minCreatedAt}
  ORDER BY created_at DESC LIMIT 1
  ```

- 或者：**规则化报告不入存档**（`archive()` 只在 `model != "rule-based"` 时调用）。
  规则化报告是纯计算、无成本，本来就不需要省这次计算。

> `idx_ai_report_code_created (code, created_at)` 这条索引已经能支撑带时间条件的查询，
> 加条件不需要改索引。

### 3. `FundamentalService` 自调用，`@Cacheable` 静默失效

```java
// FundamentalService.java
@Cacheable(cacheNames = CacheNames.FUNDAMENTAL, key = "'overview:' + #code", sync = true)
public FundamentalOverview getOverview(String code) { ... }        // line 74

@Cacheable(cacheNames = CacheNames.FUNDAMENTAL, key = "'dupont:' + #code", sync = true)
public DupontAnalysis getDupont(String code) {
    FundamentalOverview overview = getOverview(code);             // line 188 ← 自调用
    ...
}
```

`getDupont` 里对 `getOverview` 的调用是**同类内部直接调用**，不经过 Spring AOP 代理，
所以那一行 `@Cacheable` 完全不生效：`overview:{code}` 这个缓存键**不会被写入**。

**危害链**：

1. 用户打开个股详情页 → `GET /fundamental/{code}`（写 `overview:code`）
   与 `GET /fundamental/{code}/dupont`（读不到 `overview:code`，自己再打一次上游）
   可能并发或先后发生；
2. dupont 那条路径会**重复执行 `fetchFundamental` + `fetchFinancialPeriods` +
   `fetchBoardValuation`**，即一次页面访问多打 2~3 个东财接口；
3. 东财存在 **IP 级风控**（README §5.2 已实测），重复请求正是触发风控的催化剂——
   而这个缺陷**让请求量凭空多出一倍**。

**修复建议**：

```java
// 方案 A（推荐）：注入自身代理，跨方法调用走代理
private final ObjectProvider<FundamentalService> self;
...
FundamentalOverview overview = self.getObject().getOverview(code);
```

```java
// 方案 B：把 overview 的计算抽到独立的内部 Bean（@Service FundamentalLoader），
//          两个 @Cacheable 方法都调用它，缓存放它身上
```

> 项目里其他 `@Cacheable` 都是跨 Bean 调用（`ResilientMarketDataProvider` → provider 代理），
> 不受影响。**只有这一处是自调用**。
>
> 顺便提醒：`@Cacheable` 和 `@RateLimit` 都是基于代理的注解，
> 「自调用失效」是同一个坑——值得在 README 的"踩坑"章节补一条。

## 三、P1：值得做（性能 / 稳定性 / 可运维性）

### 4. 降级链顺序硬编码，运行时不可调

```java
// MarketDataSupportConfig.java:94
router = new ResilientMarketDataProvider(
        List.of(eastMoneyProvider, tencentProvider, mockProvider),
        properties.fallbackToMock(), cooldownMillis, meterRegistry);
```

链顺序写死在 `@Bean` 方法里。但 README §5.2 的实测结论是：**东财不可达是按路径、间歇性的**，
而腾讯 `qt.gtimg.cn` 稳定可用。现在的应对手段只有两种：等 30 秒冷却自动放行探测（恢复检测
最多延迟一个冷却周期），或者改代码重启。

**建议**：把链顺序改成配置项。

```yaml
app:
  market-data:
    chain: ${MARKET_DATA_CHAIN:eastmoney,tencent,mock}   # 逗号分隔，缺省保持现状
```

`MarketDataSupportConfig` 按名字解析成 provider 列表即可。这样在东财风控期可以一条环境变量
把腾讯提为主源，无需改动代码——对"上游时通时断、任何可达性结论只对当时那一刻成立"
（README §八 的原话）的场景，这是最直接的运维杠杆。

> 注意保留一个保护：`mock` 必须始终在链尾存在，否则离线演示配置会挂。

### 5. 上游只支持 JDK HttpClient，疑似被 TLS 指纹拦截

`RestClientConfig.buildClient` 唯一使用的底层实现是 `JdkClientHttpRequestFactory`：

```java
HttpClient httpClient = HttpClient.newBuilder()
        .connectTimeout(timeout)
        .followRedirects(HttpClient.Redirect.NORMAL)
        .build();
JdkClientHttpRequestFactory requestFactory = new JdkClientHttpRequestFactory(httpClient);
```

而 README §5.2 已经实测记录：**同一请求，`curl` 带浏览器 UA 拿到完整数据，
JDK `HttpClient` 在 TLS 握手后被静默断连（`HTTP/1.1 header parser received no bytes`）**。

这说明 UA 头不是决定性因素——**决定性因素是客户端 TLS 指纹**（JA3/JA4）。
`HttpClient.newBuilder()` 默认走 **HTTP/2 + ALPN 协商**，且 JDK 的 ClientHello 特征
（密码套件顺序、扩展集合、椭圆曲线偏好）与 OpenSSL/浏览器差异明显，
很容易被 WAF（东财有）识别为非浏览器流量而直接断连。

**建议按成本从低到高做三步实验**（每步都很便宜，值得实测记录）：

1. **强制 HTTP/1.1 并关掉 h2 协商**——一行改动，直接验证"是不是 ALPN 引起的"：
   ```java
   HttpClient.newBuilder()
           .version(HttpClient.Version.HTTP_1_1)
           .sslContext(...)   // 需要显式构造，避免默认 ALPN h2
   ```
2. **换底层实现**：把 `JdkClientHttpRequestFactory` 换成 Apache HttpClient 5 的
   `HttpComponentsClientHttpRequestFactory`（OpenSSL/BoringSSL 系指纹）。
   RestClient 只依赖 `ClientHttpRequestFactory` 抽象，**换实现不需要改任何业务代码**。
3. 仍不行则考虑商业数据源（README §八 已建议）。

> 这一条的价值在于：它是 README §5.2 / §5.3 / §八 反复出现的那条"真实行情链路未验证"
> 的**根因假设**，而当前 README 只描述了现象、没有给出可执行的排查方向。
> 建议把上面三步实验的结果补进 README——**哪怕实验结果是否定的，也是有价值的信息**。

### 6. 首页轮播串行取价

```java
// QuoteService.java:126
for (String code : shuffled) {
    if (items.size() >= count) break;
    try {
        Quote quote = marketDataProvider.getQuote(code);   // ← 串行，逐个 await
        ...
```

`CAROUSEL_CANDIDATES` 有 10 只，前端首页请求 `carousel(6)`。冷缓存（`quote-ttl: 3s`，
首屏必然冷）时就是 **6 次串行上游往返**；若前几只取数失败，最坏要串行尝试 10 次。

同一个项目里 `QuotePusher.fetchQuotes` 已经明确用「按 24 只分块 + 并行」解决了同一个问题，
注释里还写了为什么要并行（"100 只标的、每只 200ms 就是 20 秒"）。
**轮播这条路径漏掉了同样的处理**，是明显的不一致。

**建议**：复用 `marketFetchExecutor`，用 `CompletableFuture` 并行取这批候选，
再按原顺序收集前 `count` 条。失败跳过、不阻塞整批的语义保持不变。

### 7. 超时预算三层不一致：最坏 36s vs 前端 20s

单次行情请求的耗时上限不是 `timeout: 6s`，而是：

```
connectTimeout(6s) + readTimeout(6s) = 12s / 每级
× 3 级降级链（eastmoney → tencent → mock）≈ 36s
```

（`JdkClientHttpRequestFactory` 的 `setReadTimeout` 与 `HttpClient.connectTimeout`
是两个独立的超时，注释里"设得比页面等待时间短"只覆盖了其中之一。）

冷却机制（`upstream-cooldown: 30s`）能缓解**后续**请求，但**冷却到期后的第一次探测**
仍可能走满三级。此时：

| 环节 | 预算 |
|---|---|
| 后端最坏 | ~36s |
| 前端 axios | **20s** ← 先放弃 |
| Nginx | 120s |

**建议**：把连接超时与读超时拆成两个配置项（如 `connect-timeout: 2s` + `timeout: 6s`），
让最坏值收敛到 `3 × 8s = 24s` 以内；或者干脆给降级链设一个整链总预算。
无论选哪种，**三个数字应该写在一起并互相校验**，而不是散落在 yml、Java、nginx 三处。

### 8. `.tmp-probe/` 残留 161 MB，且未被忽略

```gitignore
.tmp-probe/
```

同时确认它可以安全删除（纯临时产物，删掉不影响任何源码）。

### 11. 两个接口缺 `@RateLimit`

逐控制器统计 `@GetMapping/@PostMapping/...` 与 `@RateLimit` 的数量：

| 控制器 | 映射数 | 限流数 | 缺口 |
|---|---|---|---|
| `AuthController` | 6 | 5 | **`POST /auth/logout`** |
| `NewsController` | 2 | 1 | **`GET /news/channels`** |
| 其余 6 个控制器 | — | — | 一一对应，无缺口 |

`logout` 是写操作（会往吊销存储里写记录），漏掉严格桶意味着它可以被无限刷——
在 `SESSION_STORE=redis` 下这等于给 Redis 制造无上限的写入压力。

**建议**：给 `logout` 补 `@RateLimit(RateLimitScope.STRICT)`；`/news/channels` 是纯静态清单，
补 `LOOSE` 或明确加注释说明"有意不限流"。

## 七、值得肯定的设计

走查中确认到几处"看起来普通但做了正确取舍"的地方，修复上述问题时**不要顺手破坏它们**：

- `ResilientMarketDataProvider` 把「记状态」和「抛异常」收进统一的 `degrade()` 入口，
  先判开关再决定记不记——避免了"关闭降级却仍上报已降级"的语义污染（README 第六节第 10 条）。
- `degraded()` 只认**链尾演示源**，中间备用真实源（腾讯）接管时保持 `false`——
  「真实行情不挂演示警示」这条判断是对的，改链顺序时（P1-4）必须保留。
- `http.ts` 区分 `AUTH_EXPIRED` / `AUTH_INVALID` / `AUTH_REQUIRED` 三种 401，
  且对刷新做了单飞（single-flight）——对应后端刷新令牌轮转语义，逻辑是自洽的。
- 前端所有来自上游的文本（新闻标题、股票名）都走文本插值、代码里明确写了"不要改成 v-html"。
- 数据库设计：`UNIQUE KEY uk_holding_user_code` + `UNIQUE KEY uk_watchlist_item_user_code`
  让"并发首次买入/重复加自选"从"会不会发生"变成"结构上不可能"，
  并且应用层是**捕获约束冲突**而不是"先 SELECT 再 INSERT"——这是正确的写法。
