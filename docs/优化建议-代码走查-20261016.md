## 二、P0：建议先修这三条

### 1. 后端已经异步化了，前端还在走同步 45 秒

这是本次走查**最重要的一条**：后端这轮新增了一整套异步分析任务机制，但前端一行都没接。

**后端已建成的部分**（都已就位、可直接使用）：

| 组件 | 位置 | 作用 |
|---|---|---|
| `POST /api/v1/analysis/{code}/async` | `AnalysisController:133` | 校验代码后立即返回 taskId（HTTP 202） |
| `GET /api/v1/analysis/tasks/{taskId}` | `AnalysisController:153` | 轮询状态与结果 |
| `AnalysisService.submit / task` | `AnalysisService:111,125` | 编排层异步入口 |
| `AnalysisTaskExecutor` | 全文 | 后台线程跑生成，不占 Tomcat 线程 |
| `analysisTaskThreadPool` | `AsyncConfig:66` | 与行情线程池隔离，`AbortPolicy` |
| `analysis_tasks` 表 | `V2__analysis_tasks.sql` | 任务持久化 |

**前端现状**：

```ts
// frontend/src/api/endpoints.ts:217 —— 只有这三个，没有 async 提交、没有轮询
export const analysisApi = {
  get:        (code) => api.get<AnalysisReport>(`/analysis/${encodeURIComponent(code)}`),
  regenerate: (code) => api.post<AnalysisReport>(`/analysis/${encodeURIComponent(code)}`),
  history:    (code, limit = 10) => api.get<AnalysisReport[]>(`/analysis/${encodeURIComponent(code)}/history`, { limit }),
}

// frontend/src/views/AnalysisView.vue:104 —— 仍在同步等那一次 45 秒的大模型调用
report.value = await analysisApi.regenerate(code.value)
```

```ts
// frontend/src/api/http.ts:90 —— 全局 20 秒，且 api.post 没有 timeout 参数可覆盖
const http = axios.create({ baseURL: '/api/v1', timeout: 20_000 })
```

**后果（两层）**：

1. **异步化的收益是 0**。`AnalysisTaskExecutor` 的类注释写得很清楚——异步化是为了消除
   「约 5 个并发分析请求吃掉大半 Tomcat 线程池」。但只要前端继续打同步的
   `POST /analysis/{code}`，请求线程照样在等大模型，线程池问题原样存在。
   后端的改造等于做了 but 没接上。
2. **配了 LLM Key 后「重新生成」必然前端先超时**。20s（axios）< 45s（`app.llm.timeout`），
   而 45s 是上限不是预期值——用户会在 20 秒看到「无法连接服务器」，后端其实还在跑，
   几十秒后把报告写进 `ai_reports`，用户再点一次又超时。
   **这正是第一轮走查的 P0-1**，后端换了做法（异步），但前端没跟上，问题本身没变。

**修复建议**（推荐两条一起做）：

```ts
// ① 接异步：endpoints.ts
submit: (code: string) =>
  api.post<AnalysisTaskSubmission>(`/analysis/${encodeURIComponent(code)}/async`),
task: (taskId: string) => api.get<AnalysisTaskView>(`/analysis/tasks/${taskId}`),
```

```ts
// ② AnalysisView.vue：提交后轮询到终态，配指数退避（3s → 上限 60s），
//    并在轮询期间给出进度提示，而不是一个转圈等 45 秒
```

> 注意 `GET /analysis/{code}` **没有存档时也会触发生成**（`AnalysisService:92-97`），
> 走的是同步路径。所以接异步的同时，GET 要么放宽超时、要么也改成「读存档 + 无存档则提交异步任务」，
> 不能只改 POST。

### 2. AI 报告存档没有时效，降级报告会被永久固化

第一轮已提出，本轮核验**未修复**，且异步路径让影响面变大了一点。

```java
// AiReportMapper:31 —— 没有任何时间条件
@Select("SELECT * FROM ai_reports WHERE code = #{code} ORDER BY created_at DESC LIMIT 1")
AiReport selectLatestByCode(@Param("code") String code);
```

`AiReportArchiver.loadLatest`（:43）拿到就返回，不做时效判断；
`AnalysisService.analyze`（:83-88）有存档直接返回、不重新生成。

两个后果：

1. **规则化降级报告被永久固化**。没配 Key 时 `ruleBased()` 生成的报告也会 `archive()` 落库。
   之后即使配好了 Key，`GET /analysis/{code}` 仍然返回那份 `model=rule-based` 的旧报告，
   必须用户手动点「重新生成」才换得掉。对「上了 Key 但结果还是规则化」的排查者来说很难定位。
2. **报告里的价格是死的，措辞却是「最新」**。正文由 `ruleThesis()` 拼出
   「贵州茅台（600519）最新价 1685.00，当日 +1.23%」，原样存进 `report_json`。
   三天后再 GET，页面仍显示「最新价 1685.00」。

**新增影响面**：异步任务也往同一张表归档（`AnalysisTaskExecutor:106`），
所以「一次降级、长期复用」现在有两条写入路径。

**修复建议**（任选，推荐前两条一起做）：

```sql
-- 加时效窗口，做成配置：app.analysis.archive-max-age: 6h
SELECT * FROM ai_reports
WHERE code = #{code} AND created_at >= #{minCreatedAt}
ORDER BY created_at DESC LIMIT 1
```

- 或：**规则化报告不入存档**（`archive()` 只在 `model != "rule-based"` 时调用）。
  规则化报告是纯计算、零成本，本来就不需要省这次计算。
- `idx_ai_report_code_created (code, created_at)` 已能支撑带时间条件的查询，加条件不需要改索引。

### 3. `FundamentalService` 自调用让 `@Cacheable` 静默失效

第一轮已提出，本轮核验**未修复**，且新增的 `compare()` 把影响放大了。

```java
// FundamentalService:85 —— 缓存本身配好了，TTL 6 小时
@Cacheable(cacheNames = CacheNames.FUNDAMENTAL, key = "'overview:' + #code", sync = true)
public FundamentalOverview getOverview(String code) { ... }

// :199（杜邦分析内部）
FundamentalOverview overview = getOverview(code);   // ← this 调用，绕过代理

// :326（同行对比内部）
for (String code : codeList) {
    result.add(getOverview(code));                  // ← 每只都绕过代理
}
```

Spring 的缓存注解走 AOP 代理，**同类内部调用不经过代理**，注解直接无效。

**为什么现在是 P0**：`GET /fundamental/compare` 一次最多 6 只，每只 `getOverview` 要打
2~3 个上游接口（概览 + 行业 + 板块估值），于是单次请求放大成 **12~18 次上游调用**。
而 `FundamentalController:88` 的接口注释自己写着：

> 一次最多 6 只股票。**上限是为了避免单次请求放大成数十次上游调用。**

——注释声称的防护，被自调用架空了。这个矛盾值得直接写进注释或代码里改掉。
另外东财存在 IP 级风控（README 已记录），上游调用越多越容易触发，这条会加剧风控。

**修复建议**（三选一，推荐第一个）：

```java
// ① 注入自身代理——改动最小
private final FundamentalService self;   // 构造器注入，配 @Lazy 避免循环依赖
// 调用处改为 self.getOverview(code)

// ② 把 getOverview 抽到独立的 @Component（如 FundamentalOverviewLoader），
//    两个调用方都注入它。结构更清晰，也彻底杜绝将来再写 this.xxx

// ③ 用 @Cacheable 标注在 compare 上（治标：只挡住 compare，dupont 内部仍失效）
```

### 6. 异步链路零测试覆盖

当前 `src/test` 有 26 个测试类，但**没有一个是针对异步链路的**：
`AnalysisTaskExecutor`、`AnalysisTaskStore`、`AnalysisService.submit/task`、
两个异步端点都没有对应测试。

最该补的三条断言（都是真会出问题的分支）：

2. 报告序列化失败 → 降级记 `FAILED` 而不是让后台线程抛异常（`AnalysisTaskStore:54-63`）；
3. `taskId` 不存在 → 返回 404 `ANALYSIS_TASK_NOT_FOUND`（`AnalysisService:125-127`）。

## 四、P2

### 8. 金额用 `double`，库里是 `DECIMAL(18,4)`

```java
// HoldingService 全文
double marketValue = 0;  double costTotal = 0;
double pnl = marketValue - costTotal;
double newAvgCost = (oldShares * oldCost + shares * price) / totalShares;
```

```sql
-- V1__baseline.sql:112
avg_cost DECIMAL(18, 4) NOT NULL DEFAULT 0 COMMENT '加权平均成本'
```

持仓成本、盈亏是**记账语义**，`double` 的二进制浮点在累加与比较上都有经典陷阱
（`0.1 + 0.2 != 0.3`、大数累加精度漂移）。库里已经用了 `DECIMAL(18,4)`，
Java 侧却全程 `double`，两侧口径不一致。

**建议**：`Holding.avgCost` 与 `HoldingService` 的金额计算改用 `BigDecimal`，
在「DB 读写」与「JSON 出参」两个边界做显式转换。
若判定为自研工具、金额不涉真实交易而维持现状，也建议在 `Holding` 类注释里写清这个取舍——
**这是面试里「为什么金额不用 double」的现成素材**，能主动讲清楚比回避加分。

## 六、建议的修复顺序

1. **P0-1**（前端接异步）——收益最大：既解决了超时，又让已建成的后端异步化真正生效。
2. **P0-3**（`@Cacheable` 自调用）——改动最小（几行），直接减少上游调用量、降低风控概率。
3. **P0-2**（存档时效）——改动小，消除一个很难自查的数据陈旧问题。
4. **P1-6 / P1-7**（补测试）——把异步链路和令牌单飞逻辑纳入 CI 保护。
5. **P1-4 / P1-5**（并行取价、降级链可配置）——性能优化与运维灵活性。
6. P2 各条按心情排。

## 七、值得保留的做法（不要动）

走查中看到几处明显优于常见实现的设计，改动时请确保不破坏它们：

- `ResilientMarketDataProvider` 的**「策略性拒绝编造」**：榜单在降级路径上直接返回 503，
  而不是给出「看起来合理的假榜单」（类注释 72-95 行）。这条是数据诚实性的核心。
- `ResilientMarketDataProvider.degraded()` 的语义收窄：备用**真实源**接管时不算降级，
  只有链尾演示源服务才算——避免给用户挂假的警示横幅。
- `JwtTokenService` 的 `sid` 声明：让登出不依赖客户端配合，服务端可自行裁决会话。
- `HoldingService.insertNewHolding` 对 `DuplicateKeyException` 的处理
  （含「PostgreSQL 下会 aborted、本项目只支持 MySQL/H2」的显式边界说明）。
- `AiReportArchiver` / `AnalysisTaskStore` 一以贯之的「**存档失败不影响主流程**」。

### 8.12 前端补齐：工程基建 M0、行情体验 M1~M5

第八节前面几条都在后端，前端还留着四条体验与合规缺口。按 M0 → M5 顺序补完：

| 项 | 缺口 | 落地 |
|---|---|---|
| **M0 工程基建** | 存储键散落无规范；埋点无处可发；请求不可中止 | `utils/storage.ts`（`股票分析师.<模块>@<配置>@<版本>` + 隐私模式 try/catch 降级）、`utils/track.ts`（开发 console，生产留 `sendBeacon` 钩子）、`api/http.ts` 增加 `RequestOptions{ signal, timeout }` |
| **M1 报价头** | 合规要求「使用非实时行情必须在**价格附近**明示延迟时长」，原先只有页脚一行 | `components/QuoteHeader.vue`：延迟徽标与现价同行；补总市值、市盈率 TTM；`tabular-nums` + baseline 对齐满足「价格变化 500ms 内不闪烁重排」 |
| **M2 K 线图** | 主图与副图是两个独立实例，光标只在各自图内出现 | `components/StockChart.vue`：**单 ECharts 实例 + 3 个 grid**，`axisPointer.link.xAxisIndex='all'`；阳线空心（填充透明 + 红边）；`minValueSpan:30` + `zoomLock`；分时左价右百分比双轴手动对齐 |
| **M3 AI 解读卡** | 详情页没有 AI 入口，只能跳新页等 45s | `components/AiInsightCard.vue` + `composables/useAnalysisTask.ts`：先读存档（快速命中），未命中才 submit + 退避轮询；**默认不自动跑**（避免烧模型额度）；免责声明贴着结论 |
| **M4 板块榜单** | 只有个股榜，看不出资金去向 | `components/SectorBoard.vue`：涨跌幅 + **涨/跌家数**（加权平均会掩盖内部分化，这两个数字是对涨跌幅的自校验）+ 领涨股 |
| **M5 主题与体积** | 涨跌色写死在组件里；无暗色主题 | 涨跌色统一收敛到 `--color-up/down`，图表线色走 `--chart-*`，并新增 `--color-surface-muted` / `--color-border-strong` / `--color-warning`；新增 `stores/theme.ts`（跟随系统/亮/暗三态）+ 顶栏切换；`index.html` 加内联防闪脚本 |

三条值得一提的设计取舍：

1. **M2 为什么必须单实例多 grid**：`axisPointer.link` 只在同一个实例内成立，
   跨实例无法互相感知。原来「两幅图叠在一起」看着像联动，实际对照不了同一时刻的量价，
   而这恰恰是看盘最核心的动作。
2. **M3 为什么默认停在 idle 不自动跑**：一次生成要花一次模型调用，
   用户可能只是路过看行情，自动触发会在他不关心时把额度烧掉。
3. **M5 免责声明为什么做成组件**：同一句「不构成投资建议」散落在个股页、
   AI 研判页、自选页，靠人肉复制迟早走样。合规文本的特点是一个字都不能有差异，
   所以措辞收敛到一处，各页面只决定放哪、什么语气。

**体积核验（M5 硬指标）**：ECharts 由全量引入改为按需注册后，
`echarts` chunk 从 **1117 kB / gzip 370 kB** 降到 **597.26 kB / gzip 200.57 kB**，
降幅 46%。当前首屏主包（`index`）39.34 kB / gzip 15.94 kB。
