# 今日涨幅榜数据源改造（2026-10-21）

## 1. 问题

首页「今日涨幅榜」整块不可用：

> 市场榜单暂不可用：上游数据源故障，且该类数据不使用内置演示数据替代

顶部还挂着「暂不可用」，整块区域只有一张空图。这个面板是首页唯一直接给出
「今天涨得最好的是谁」的地方，它一死，首页就只剩指数和资讯。

## 2. 根因（三条，均已实测）

### 2.1 个股榜单只有东财一条真实源

`getTopMovers` 此前只有 `EastMoneyMarketDataProvider` 一个实现。
腾讯虽然已是备用真实源，但它的个股榜接口实测没有数据：

```
GET https://proxy.finance.qq.com/cgi/cgi-bin/rank/pt/getRank?board_type=hs&sort_type=price&direct=down&offset=0&count=5
→ {"code":0,"msg":"ok","data":{"rank_list":[],"offset":0,"total":0}}
```

于是有效链其实是 `eastmoney → mock`，而 `mock` 对榜单类操作**策略性拒绝**
（`acceptableAsFallback` 对 `getTopMovers` / `getSectors` 返回 `false`，因为名次携带判断，
编造的排序比乱码更危险）。**东财一挂，整块 503 是必然，不是偶发。**

### 2.2 东财 `clist/get` 会单次返空 / 直接断连

改造时东财正处于 IP 级风控：`push2` 的请求以
`ResourceAccessException: I/O error ... header parser received no bytes` 失败，
四个镜像域（`push2` / `1.push2` / `82.push2` / `push2delay`）同时断，
而新浪同一时刻正常——单源风险，不是本机网络问题。

同一天还观察到另一种更隐蔽的形态：**单次返回空数组，立刻重发就成功**。
此前只有板块榜为这个形态加了重试，个股榜单没加（当时的判断是「调用方本来就有多个榜可看」——
但首页那个榜单并不会有「别的榜可看」）。

### 2.3 缓存键不带源前缀（接第二家源后才会暴露）

东财榜单用 `CacheNames.QUOTE` 这组缓存、键是 `'movers:...'`。
只要再有一个源用同一个缓存名和同样的键，东财恢复后会命中另一个源缓存的列表，
表现为「板块数量在 60 秒内自己变了」，且不报任何错。板块榜已经在 2026-10-21 上午踩过同一个坑。

## 3. 改动

| # | 改动 | 原因 |
|---|---|---|
| 1 | 新增 `SinaMarketDataProvider`（`market/sina/`），实现 `getTopMovers` | 让榜单有两个真实源；`node=hs_a` 覆盖与东财完全相同的五个板块（沪深主板/创业板/科创板/北交所） |
| 2 | 新增 `app.market-data.movers-chain`（默认 `eastmoney,sina`），复用已有的「按操作覆盖降级链」 | 只影响 `getTopMovers`；新浪在本项目里**只**有榜单能力，放进主链会让每次报价/K 线降级多走一次注定失败的调用 |
| 3 | 东财榜单改用共用的 `fetchClistWithRetry`（2 次 / 120ms 退避，与板块共用） | 空数组与断连都是「这次没拿到」。首页这块**只在挂载时取一次、不轮询**，一次抖动会一直空到用户手动重试 |
| 4 | 两个源的榜单缓存键都加源前缀（`eastmoney:movers:` / `sina:movers:`） | 见 2.3 |
| 5 | `MarketSourceStatus.displayNameOf` 补 `sina` / `tushare` | 主源可配成任一家，缺条目时顶栏显示裸英文标识 |
| 6 | 前端：`utils/marketSourceLabels.ts` 抽出「源标识 → 展示名」，`SectorBoard` / `HomeView` / `MarketView` 共用 | 三处各写一份映射，迟早出现「板块写腾讯、首页写 tencent」 |
| 7 | 首页「今日涨幅榜」加来源标签与**重试按钮**；失败保留上一批数据 | 来源影响可见结果（两家榜单名单不同），必须标；5xx 重试是用户此时唯一能做的事 |

### 3.1 新浪实现的四处刻意处理

1. **排序在本地做**：`sort` / `asc` 的行为没有文档保证，而接口契约是「按该维度排序的前 N 条」。
   拉回 20 条上下重排一次，成本可忽略，换来可断言的性质（跌幅榜第一行确实最跌）。
2. **多取 5 条再截断**：停牌行 `trade="0.000"` 会被丢弃（否则上榜被读成「股价归零」），
   按 `limit` 精确取数时返回条数会少；多取几条比多请求一次便宜。
3. **编码不盲信响应头**：头里写 `charset=gbk`，正文实际是纯 ASCII + `\uXXXX` 转义。
   先按 UTF-8 严格解码、失败再退 GBK——万一上游改成 UTF-8 原文，按 GBK 解会得到
   一串乱码股票名且**不报错**，这种静默错乱最难查。
4. **能力边界如实声明**：报价 / K 线 / 指数 / 搜索四个方法直接抛「不可用」，
   不塞一个只能查到局部数据的假实现。

## 5. 口径与已知限制

- **两家榜单名单不完全相同**：涨跌幅榜头部同为新股（如 `N文峰 +217%`），
  但 10~20 名区间会因「停牌过滤、ST 处理、数据刷新时点」出现差异。
  这一点在界面上通过来源标签如实暴露，**不做「两源合并」**——合并等于编造一个不存在的榜单。
- **收盘后两家都给收盘值**，`ticktime` 停在 15:30 左右；接口不提供「数据是否延迟」的声明，
  因此 `quoteDelayMinutes` 仍为 0（实时源）。
- **新浪只有榜单能力**。若要让它接管报价，需要另接 `hq.sinajs.cn`（需要 Referer、GBK 文本、
  字段口径又是一套），属于独立改动，本次没做。
- **东财仍排第一**：两家都能用时不会切换到新浪，避免日常抖动。
